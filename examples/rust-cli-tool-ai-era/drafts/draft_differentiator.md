## 草案：`stet` — 「AIの出力は未固定の依存だ。今日からCargo.lockにしろ。」

**① ツール名とキャッチコピー** — それは `stet`。校正記号の「このまま残せ」に由来する。AI生成物を、作者不明・入力不明・再現不能な「未固定の依存関係」として扱うのをやめるツールだ。

**② 解消する課題と対象** — AI時代の本命の痛みは生成不足ではなく**出自不明の供給網**である。プロンプトがひとつ変われば本番ロジックが無言で書き換わるのに、`git blame`には人が出るだけで「何がコードを変えたのか」を追跡できる道具が存在しない。`cargo build`が左パッド事件を防いだように、`stet`は出力の出自を鎖で繋ぐ。対象はAI生成コードを本番へ投入するエンジニアと、出力の監査義務を負う組織。これはプロンプト管理ツールではない——保存するのは「プロンプト」ではなく「成果物の証明」だ。生成より検証が先。この順序が唯一の正解である。

**③ 主要機能**
- `stet pin <file> --model sonnet-4 --input src/,spec.md --prompt gen.md` — 成果物を固定。プロンプト本文・入力全ファイルのハッシュ・モデルと温度・出力ハッシュを`stet.toml`に記録。
- `stet verify` — 完全オフラインで再検証。入力が変わっていれば「破損依存」として報告。ネットワークもAPIも不要。
- `stet blame <file>` — ハッシュ索引を逆引きし「このコードは、このプロンプトとこのコミットから生まれた」と出自を表示。
- `stet diff <file>` — 固定版と最新版のドリフトを行単位で検出し、どのプロンプト更新がこのロジックを書き換えたか特定。
- `stet status` — `git status`のように未固定のAI成果物を列挙（マーカーコメント `// stet:<id>` から逆引き）。

```
$ stet verify
✗ src/api.rs   DRIFT: input spec.md changed → re-pin
✓ src/ui.ts    ok
```

**④ Rustを選ぶ理由** — 実体は「全ファイルの高速ハッシュ×TOML処理×リポジトリ走査」であり性能が正義。`blake3`と`ignore`（ripgrep由来）で巨大リポジトリを一瞬で走査し、単一静的バイナリは監査用CIにランタイムごと放り込める。加えて、悪意あるリポジトリを読み込む攻撃面ではメモリ安全が必須であり、「ロックファイルで信頼できない依存を制御する」という発想自体がCargo、すなわちRust自身の文法からの借り物だ。

**⑤ シンプルさ** — 依存は`clap`・`blake3`・`toml`・`ignore`の4クレートのみ。検証コアはハッシュ比較だけで1000行に満たず、LLMへの依存は`stet pin`の生成実行時ただ一箇所に隔離される。一度固定すれば再現は環境・OS・時刻に依存しない完全決定論で、ドリフトは「入力が変わった」と「モデルが変わった」の二値にしかならない。

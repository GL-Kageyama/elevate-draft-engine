# DOF Reality HERO H3 —— 体感ゲーム用モーションプラットフォーム企画

`elevate-draft-engine` の `elevate` で、**DOF Reality HERO H3**（3軸モーションシミュレータ）を土台にした企画を出した記録である。

各 `run-NN/` は**独立した1回の実行**で、自分の `input.md`・`knowledge.md`・`drafts/`・`artifacts/` を持つ。

```bash
.venv/bin/python main.py elevate "<タスク>" \
  --lang ja --engine claude-code --method two-stage --idea-level standard \
  --knowledge-file <前提知識> \
  --out examples/dof-h3-app-ideas-ja/run-NN
```

## タスク

2系統ある。

**A —— 個人向けアプリ**（run-01）

> DOF Reality HERO H3（3軸モーションシミュレータ）を PC から駆動して楽しむ、シンプルに作れてシンプルに楽しめるアプリ（ソフトウェア）のアイデアを企画出しせよ。レーシング／フライトシミュレータの焼き直しではないこと。

**B —— 公共遊具**（run-02〜run-04）

> 「AI体感ゲームセンター」に置く一つのゲームとして、体感ゲーム用のモーションプラットフォームを設計せよ。最新のAIを核とし、公共の場で子どもを含む不特定多数が遊ぶ遊具として成立すること。レーシング／フライトシミュレータの焼き直しではないこと。

**同じ hardware.md から出発しながら、拘束条件が違う。** B では来場者は持ち主ではなく、係員は常駐せず、説明は読まれず、子どもが一人で乗る。A の「シンプルに楽しめる」は一人の趣味の話だが、B のそれは**不特定多数が説明なしで回れる**という意味になる。

## 各 run の成果物

### run-01 —— 「重力の感じ方」を書き換える機械のためのアプリ

企画提案書。**前庭（耳の奥にある平衡感覚の器官）が受け取るのは角度ではなく「重力ベクトルのずれ」**だという定式化から出発し、20°の狭さを**欠如ではなく前庭への特化**と読み替える。そこから5案（呼吸／共有／揺れのボイスメモ／地震／アンコール）を出し、**A. 呼吸が決める重力の感じ方**を推奨。共通ランタイム（クランプ・スルーレート・15秒ハートビート・原点復帰・1キー中央復帰）の上に、他の案を**プリセット**として足していく構造を取る。

### run-02 —— 『シタオリ』

設計書。**90秒・3相**（読まれる／織られる／返る）。AIが「あなたの重力の感じ方」を推定し、閾値直下のゲインで書き換え、最後に **BODY TAPE** と一行のモデルとして返す。**人がループの外から中へ移る**——操作者ではなくループの一部になる。座位・骨盤のみ拘束・上半身非拘束で、**抗いを残す**。

### run-03 —— 『明け渡しの深さ』

設計仕様書。中心は **σ＝身体の制御を台に明け渡す深さ**。σ は二重性を持つ —— 姿勢・支持・拘束として外から見える **σ_out** と、筋緊張・重心動揺・把持力・呼吸として本人にも正確にはわからず **AIが推論するしかない σ_in**。**この二つのズレがゲームの全体**である。操作機器ゼロ。

### run-04 —— まわしよみ（回し読み）

設計仕様書。**前の人の身体についてのAIの仮説**が台に載っており、あなたはそれを身体で試し、抗い、次の人へ一行だけ残す。**自分の読みは最後まで自分には見せられない。** 軸の自由度を諦めたぶんが観客の自由度に回る（**軸自由度の不足が、社会自由度の増加を強制する**）。設計の要は**二チャネル分離** —— 台を動かす経路は正確で AI を通さず、AI が触るのは意味の側だけ。

> run-04 は `visionary` の草案生成が3回連続で打ち切られ、**7体で昇華されている**（エンジンのエージェント単位エラー捕捉による。他の run は8体）。

## 4つの成果物に共通する読み方

- **3軸の制約を欠陥ではなく設計条件として扱う。** どの run もヒーブ／サージ／スウェイを前提にしない。上下動は傾きによる錯覚（チルト・コーディネーション）のみ。
- **画面を主役にしない。** 4つとも、意味は画面ではなく身体で完結する。
- **ルートA（モーションボックスへ直接シリアル）を主とする。** ファームウェアは指令値を検証しないので、**制限を守る責任はホスト側にある**。

タスクB（run-02〜run-04）には、これに加えて共通する姿勢がある。

- **AIを演出に使わない。** 難易度調整や見た目の生成ではなく、**身体を読む／身体を仮定する**側に置く。「AIの身体性の欠如そのものを扱う」ことが、構想の中心命題への応答になっている。
- **有料ライセンスに依存しない**ことを明示している。ルートA は `pysmc3`（Apache-2.0）で完結し、SRS を介さない。

## 付録（読解ガイド）

run-03 と run-04 の `artifacts/` には、**本文と同じ階層に**読解ガイドが置いてある。

| ファイル | 何をするか |
|---|---|
| [run-03/artifacts/elevated-appendix.md](run-03/artifacts/elevated-appendix.md) | 『明け渡しの深さ』を、σ／σ_out／σ_in・上位ガバナ／下位AI・クランプ220〜803・転倒閾値の数式などの語から解く |
| [run-04/artifacts/elevated-appendix.md](run-04/artifacts/elevated-appendix.md) | 『まわしよみ』を、一行の仮説・二チャネル分離・生成包絡・台の天候・一日で消える図書館などの語から解く |

どちらも**同じ7節立て**である —— ①30秒でわかる全体像 ②中心概念 ③用語集 ④**数値の読み方** ⑤本文の構成 ⑥未解決課題の言い換え ⑦読むときの注意。

**④の「数値の読み方」が両方に共通する要**である。本文の数値は出所が3種類混ざっている —— ①販売ページ記載の確定仕様、②プロトコル仕様、③**実機の実測報告（＝単一情報源）**。③は鵜呑みにできない。

**付録はエンジンの生成物ではない。** `drafts/` と `artifacts/reconciliation.md`・`artifacts/elevated.md` は engine が保存したものだが、`elevated-appendix.md` は**後から人間向けに書いた同伴資料**である。例外として、run-01・run-03 の `elevated.md` には**「前庭」の初出に語の注記だけを後から差し込んである**（本文の主張・数値には触れていない）。

## 読み方

- **まず `artifacts/elevated.md` を読む。** `drafts/` と `reconciliation.md` は、その成果物がどう組み上がったかの記録である。
- **run-03 と run-04 は付録から入るほうが速い。** 本文は語を定義せずに使うため、付録なしでは用語集を自分で作ることになる。
- **`format.md` は run ごとに違う。** 本文の見出しは、タスクから動的に抽出された出力形式に従う。同じタスクでも run-03 と run-04 では節立てが異なる。
- **「前庭」は「前提」ではない。** どちらも「ぜんてい」と読む同音異義語である。前庭は耳の奥にある**平衡感覚の器官**で、run-01・run-03 の本文が使うのはこちらの意味（例：「VRは前庭に何も来ない」「乗員の前庭が答え合わせをする」）。**同じファイルに通常の意味の「前提」も出てくる**（`drafts/` では各節の前提を `*前提*：` と頭に付ける）。詳しくは [run-03 の読解ガイド](run-03/artifacts/elevated-appendix.md) §3・§7。
- **`knowledge.md` が run の条件そのものである。** 同じタスクでも、ここが違えば別の設計が出る（run-03 と run-04 は同一の前提知識で、独立に2つの設計を出している）。

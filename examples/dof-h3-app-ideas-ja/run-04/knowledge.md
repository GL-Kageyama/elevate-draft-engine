## 0. 何を設計するのか（位置付け）

設計対象は、**「AI体感ゲームセンター」に置かれる一つのゲーム**としての
**「体感ゲーム用のモーションプラットフォーム」**である。

**これは個人の趣味のアプリではない。公共の場に設置され、不特定多数（子どもを含む）が
次々に触る遊具である。** この違いが要求を根本から変える。

設計すべきは「**来て、座って、遊んで、降りて、次の人が来る**」設備であり、
それでいて**構想の中心命題（第6章）を満たす**ものである。

## 2. できること／できないこと（運動能力の制約）

3軸機であり、**6自由度ではない**。

**できる（3軸回転）**
- **ピッチ** … 前後の傾き（加速感・ブレーキ感・機首上げ下げ）
- **ロール** … 左右の傾き（旋回の遠心力・傾き）
- **ヨー／リアトラクション** … 後部モーターによる横滑り・向き変化
- 得意なのは**短く鋭い動き**と、**低速域の滑らかな軌道**。
  範囲が狭く速度が高い＝**小さく速い運動に最適化**されている。

**できない（並進）**
- **ヒーブ（上下）／サージ（前後）／スウェイ（左右）の並進移動は不可**。
- 段差・着地・浮遊・前進そのものの移動感は出せない。
- 上下動は**傾きによる錯覚（チルト・コーディネーション）でのみ**扱える。
- **0.7G ＝ 1G 未満**であり、実加速度の完全再現は原理的に不可能。
  **この機械が扱えるのは、実加速度そのものではなく、その知覚である。**

**時間特性**
- 可動範囲 **20° は狭い**。大きな揺れは物理的に不可能。
- 速度 **86°/秒 は速い**。→ 短く鋭い動きが得意。
- **1000W ピーク**。連続的な激しい運動は電力・発熱・騒音・摩耗で不利。

**騒音・設置**：3基のモーターとギアボックスが動く。静音機器ではない。

## 3. ソフトウェア構造と開発ルート

**確認済みのデータ経路**

```
[アプリ]  --UDP:33001-->  [SRS]  --USBシリアル-->  [モーションボックス]  --PWM-->  3モーター
                            (Arduino UNO R3)
[アプリ]  --USBシリアル 500000 baud-->  [モーションボックス]  --PWM-->  3モーター   （SRSを介さない）
```

**モーションボックス**：Arduino UNO R3 ベース、オープンソースの SMC3 スケッチ由来。
H3 は**1台**のコントロールボックスに3モーター。3軸は SMC3 が標準対応する構成そのもので、
H3 はむしろ**制御しやすい側**の機種。

**重要な排他制御**：COM ポートを握れるのは**同時に1プロセスだけ**。
SRS や SimHub が動いている間は直接制御できない（置き換えであって併用ではない）。
→ **単一ランタイム＋プリセット（＝ゲーム）構造が物理的に強制される。**

### ルートA：モーションボックスへ直接シリアル ★自由度最大・ライセンス不要

- **プロトコル**：`[` + コマンド1文字 + 値HI + 値LO + `]` の**5バイト固定長**、ビッグエンディアン
  - `[A<hi><lo>]` モーター1、`[B…]` モーター2、`[C…]` モーター3（値は **0〜1023、中央 512**）
  - `[ena]` 全モーター有効化（接続時）、`[sav]` EEPROM保存、`[ver]` バージョン
- **シリアル設定**：**500,000 baud**、8データビット、パリティなし、ストップビット1
- **既存ライブラリ**：`pysmc3`（Python、**Apache-2.0**、`pip install smc3`）。
  DOF Reality のコントロールボックスでの動作確認済みと明記。
- **H3 固有の実測知見**（実機ファーム v33.07 での報告）：
  - **約15秒コマンドが来ないと出力が絞られる（ウォッチドッグ）**。
    **アイドル時も継続的にストリームを送り続ける必要がある。**
  - ファームウェア設定により**有効範囲が狭められている**（実測例：入力クリップ 220〜803）。
  - 応答ストリームにはデバッグ文字列が混ざる。**固定長読みをしてはならない。**
  - ファームウェアは**範囲を検証しない**。**ホスト側が制限を守る責任を負う。**
- **長所**：SRS 不要、ライセンス購入不要、低遅延、3軸を完全掌握。**何でも動かせる**。
- **短所**：安全装置・レート制限・COMポート探索を**自前で実装する責任**。
  SRS/SimHub と併用不可。DOF Reality のサポート対象外。

### ルートB：SRS へ UDP パケット ★公式サポートあり・最小コード

- SRS は**公式の公開 API** を持つ（v1.43.2 以上）。サンプルは **MIT ライセンス**。
- **送信先**：`127.0.0.1:33001`、**UDP**、片方向（応答なし・認証なし）。
- **パケット**：236バイト固定。先頭3バイト `"api"`、続いてバージョン `102`。
  以降に `game` / `vehicle_name` / `location`（各50バイト）、速度・RPM・ギア、
  **pitch / roll / yaw（度）**、**lateral_velocity（トラクションロスに使用）**、
  各加速度、サスペンションストローク4輪分、路面種別4輪分。
- 公式ページは「レーシングゲーム**だけのものではない**」と明記し、
  ローラーコースター、宇宙飛行、トラック／農業シム等を想定。
  **自作の非ゲームアプリがこの構造体を送ることは、API の想定用途そのもの**。
- **長所**：公式・文書化・MIT サンプル・約30行。SRS がクセ取り・制限・
  チューニング・安全処理を担う。**すでに SRS を導入済みの機体にそのまま届く。**
- **短所**：SRS のインストールと Base License が前提。SRS のマッピングに従う。
  **生の位置は指令できず、テレメトリを渡して SRS に解釈させる**形。
  ゲームが SRS を掴んでいる間は使えない。SRS 自身が「サードパーティ製プロキシは
  クラッシュ要因になり得る」と警告している。

### ルートC：SimHub 経由

- **SMC3 コントローラーをネイティブ対応**、H3 での動作報告あり（軸の分解能を
  **10ビット**に設定する指示付き）。汎用シリアルコントローラーで任意プロトコルを定義可能。
- **短所**：**Motion Addon が有料**。プラグインからモーションを注入する方法は
  **文書化されていない**。公共設備で有料ライセンスに依存するのは配布・再現性の面で不利。

### ルートD：ファームウェア書換

- SMC3 は MIT。Teensy 移植版や他機種向け再実装が存在。**高リスク・サポート外**。

## 5. 公共設備としての安全・運用要件

H3 は**人が乗った状態で 25 N·m のトルクで動く**。しかも
**操作者と搭乗者が別人**であり、**子どもが乗る**。不具合がそのまま事故になる。

**ソフトウェア側の必須要件（ファームは範囲を検証しない）**
- **可動範囲のクランプ**（実測例 220〜803 を初期値に、実機で追測）
- **変化率制限（スルーレート）**：指令値の急変を平滑化
- **ハートビート**：アイドル時も送り続ける（約15秒でウォッチドッグ）
- **非常停止**：**誰でも即座に押せる物理ボタン**。スタッフ不在でも止まること
- **原点復帰**：起動時にいきなり飛ばさない
- **異常終了時も中央へ**戻す

**公共設備ゆえに追加で要る要件**
- **1プレイが短い**（回転率。待ち行列が成立する長さ）
- **説明なしで遊べる**（初見の子どもが座って数秒で理解できる）
- **途中で降りた／飽きた人のリセット**（次の人を待たせない）
- **体格差**：耐荷重 150kg の大人から軽い子どもまで。**体重差で同じ動きにならない**
- **衛生**：汗・髪・肌が触れる。清掃可能性
- **連続稼働**：1000W ピークの発熱、モーターの摩耗、騒音
- **いたずら・誤操作**：ボタン連打、無理な姿勢、機器への接触
- **スコアや結果を周囲と共有できる**こと（アーケードの本質。1人の体験で閉じない）

## 6. 「AI体感ゲームセンター」構想（個人名を伏せたダイジェスト）

### 6.1 構想の出発点

提唱者は、プログラミング教育の難所は**文法の習得ではなく「作りたい」という欲求を
見つけること**だと主張する。知識と技術は教えられるが、**「作りたい」という気持ちは
教えられない**。AI とバイブコーディングで「作る」こと自体が AI に委ねられた今、
**その欲求を目覚めさせるには知識伝達とはまったく別の方法が必要**である。
その方法が、彼にとっては**ゲームセンター**だった。

### 6.2 AI の実用化とゲームの関係

- CG はまず映画・CM で産業化し、次にゲームで産業化した。
- **AI の実用化は CG とゲームに依存していた**。GPU はゲームの CG のために作られ、
  家庭用ゲーム機のメーカー間競争によって**安価に大量生産**された。
  スーパーコンピュータだけでは今の AI は生まれなかった。
- ところが現在、**AI がゲーム開発にほとんど影響を与えていない**——
  AI 生成のモデル・テクスチャ・シナリオはあるが、**AI 自身の性質をゲームデザインに
  反映したものはほとんどない**。提唱者はこれを「極めて不健全」と表現する。

### 6.3 提案と価値観

**最新の AI を核にしたゲームを作り、普通の人と子どもが体験できる場所を作る。**
まず期間限定、うまくいけば常設。

**エンターテインメントの定義**：娯楽は怠惰ではなく**想像力を拡張する装置**であり、
人類が作る**最も複雑で、最も再現困難で、最も高度な道具**である。普通の道具は再利用に
耐えるが、**娯楽は再現不能で本質的に一時的**だから、常に新しい作品が要る。
だから先端技術と娯楽は共に進歩してきた。

AI 時代の2つの問い：**「技術をどう使うか」**と**「人をどう楽しませるか」**。
例として、画像認識 AI を「何の役に立つのか」と問うのではなく、**遊びに変えて
「面白い」と感じさせる**ことが挙げられている。

### 6.4 プロトタイプ筐体と試作タイトル

**筐体**：MDF 製の縦長画面の筐体。**カメラ**（表情や服装を取得＝AI の得意分野）と
**マイク**（音声）を内蔵。**ユーザーの反応を見ながら難易度を調整**し、
**音声コマンドで内容を変える**ことができる。

**試作タイトル**：一晩で作った縦スクロール・シューティング。
- ボム使用時に**プレイヤーが単語を叫ぶ**と、画像生成 AI が**自機をその単語に
  まつわる姿に変形**させる。
- **ボスと全攻撃パターンは内部の LLM がその単語から生成**する。
- **同じ攻撃パターンは二度と出ない**。それでも「**にもかかわらず、ちゃんと面白い**」
  というルールを保つ。
- 制作時間は**3時間**。

**最低技術目標**：**Raspberry Pi 5 ＋ 5060ti 単体で動くゲーム**。加えて AI 中心の
タイトルあと2本。

### 6.5 進行中の計画（実在）

- クラウドファンディング：目標 **100万円** → 約10時間で達成、200%超。
  **ネクストゴール 1000万円**。支援者特典の柱は**設計図・素材・メモ・
  ソースコードの共有**。最低額 5万円。
- **生成 AI 自体の計算資源は当初予算に含めていない**（意図的に除外）。
- ブレインストーミング、ハッカソン／コンテスト、協力者募集を計画。
- **企業のお金とクラウドファンディングのお金は違う。後者は税金のように扱う。**

**ネクストゴールで実現したいもの**：
- **対戦台**（当初計画から外れた。対戦はアーケードの華）
- **体感ゲーム**（参照例として往年のアーケードレースゲームの名作2作）
- **ガンシューティング風**（見た目はシューティング、中身は生成 AI にしか作れないもの）
- **多人数同時協力プレイ**（アーケードならでは）
- **先端 UI の実験**：ハプティクス、画像認識による新しい形。
  ※MIT MediaLab の **inFORM**（購入に1億円以上とされる）が参照されている
- 制作拠点が手狭なため、**1〜2日だけ広い場所を借りて**多様な AI ゲームを集める

**場所の目標**：まず期間限定で制作拠点の2フロア。ストレッチで**公民館や学童**へ。
長期は常設。**「ゲームセンター」という語は風営法上の問題を生じうる**ため
別の呼称を検討中。

### 6.6 ゲーム観：System 1 と System 2

- **ガチャ的な設計は System 1（本能・動物の習性）向け**であり、提唱者は理解できないと述べる。
- 自身のゲーム観は **System 2（理性・論理・戦略的思考）向け**であり、
  **System 1 を使って System 2 を成立させる**という構え。
- **System 2 を捕まえること**＝**パラメータの変動を、情動的な投資に足るものにすること**。
  これに最先端の計算資源を適用することは、次元の違う課題だと述べる。

## 7. 既存事例（重複回避のための参照）

- **レーシング／フライトシム**：100タイトル以上が SRS 経由で対応済み
- **ローラーコースター／宇宙飛行／トラック・農業シム**：SRS の API ページが想定用途として例示
- **SRS v2.9+ の Intellitune**：3分の解析で最適設定を提案する AI チューニング
- **VR モーションコンペンセーション**：SRS に統合済み
- **FlyPT Mover**：無料。SMC3 出力あり。**DOF Reality のリグ寸法プロファイルが存在しない**
- **SimTools**：旧来のモーションソフト
- **Unreal Engine「Motion Platform Linker」プラグイン**：SRS 公式の UE 連携ルート
- **往年のアーケード体感ゲーム**：特殊ハードで 300万円 した時代がある。
  構想側の参照例として往年のアーケードレースゲーム2作が挙げられている

**空白地帯**：上記はほぼ全て**「乗り物のシミュレーション」**である。
身体感覚を**他の目的**に使う事例は、ローラーコースター（＝これも乗り物）を除いて
ほとんど見当たらない。

**構想側の新しい空白**：**AI の性質そのものをゲームデザインに反映したものは
ほとんど存在しない**（6.2節）。ここが構想の狙っている空白である。

## 10. この企画で満たすべき要件

- **AI を核とする**こと。構想の中心命題は「**AI 自身の性質をゲームデザインに反映する**」。
  AI を難易度調整や見た目の生成にしか使わない企画は、構想が批判している
  「AI がゲーム開発にほとんど影響を与えていない」状態そのものである。
- **台が主役**であること。画面が主役の企画、画面があって初めて成立する企画は、
  この設備の存在理由を空洞化させる。
- **3軸の制約を正直に扱う**こと。ヒーブ／サージを前提にした企画は実機で破綻する。
- **公共設備として成立**すること。1プレイが短く、説明なしで遊べ、誰でも止められ、
  途中で降りた人をリセットでき、子どもが乗れる。
- **シンプルに作れる**こと。有料ライセンス・非公開 SDK・未文書の API への依存は、
  再現性共有の方針とも衝突するため減点。
- **「作りたい」を目覚めさせる**こと。構想の最終目的はこれである。
  **遊んだ人が「自分でも作りたい」と思うか**が、この企画の本当の評価軸である。

**三つの両立不能な立場を同時に押す**: ①初日からCIで回らねば無価値(実装)。②回る時点で既存の延長に堕す(転覆)。③成功するほど世界のコード総量と自らの存在理由が減る(自己消滅)。矛盾は捨てず、「削除」という一機構に全量押し込む。

**核心的主張**: レビューアの「このコード、本当に要る?」という毎日の守り作業を、**テストで到達不可能な全コードを物理削除し、ソースの生存を「テストという証言」に従属させるコンパイラ**に置き換える。コードは書くものでなく、証言によって日々生存確認されるものになる。

**(1) ツール名(仮称)**: `CULL`(淘汰)。`cargo install cull`。

**(2) 対象ユーザーと現在のワークフロー**: 中〜大規模リポジトリを保守するシニア開発者。防御コードと未使用依存を積み上げ、人手のレビューで死骸を探している。

**(3) 新しい枠組みで変わる流れ**: 実行すると全プログラム解析で「テストが実際に触れる到達点」を計算し、到達不能な関数・モジュール・クレート・防御分岐をソースから削除するPRを生成。各削除に死票(導入blame+証明)を添付。復活にはテスト追加が必須で、実装はテストに従属する。

**(4) Rustの4強みが必須の理由**: 性能=モノレポの到達性走査を分オーダーで。安全性=誤削除は恒久喪失。証明なき削除を型で表現不能に。依存の少なさ=消すツール自身の汚染が削除を武器化する。最小依存が信用の前提。単一バイナリ=署名検証可能な唯一の配布物で削除の再現性を担保。

**(5) 最も近い既存ツールと決定的な違い**: `creduce`(バグ再現の最小化)や`cargo-udeps`(未使用依存検出)。両者は死骸の検視に留まる。CULLは生きたリポジトリ全体を対象に、削除をコミットとして実行し、生存条件をテストの証言に書き換える。既存は検視官、CULLは火葬と墓標の設置者。

**具体的利用例**: 決済マイクロサービス(12,000行・依存30)で`cull`実行。200個のテストが触れる経路だけが残り、4,800行・14依存・9つの防御分岐が死票付きで削除されたPRが生成。CIは半分になり、レビューは「証明の検証」に変わる。将来必要になればテストを先に書き、CULLが最小実装として再構築する。

依頼は「自らの前提を問い直せ」と言う。ならば答える——私は複数の立場を抱えて折り合うのではなく、**一つの論理の内部に矛盾を封じ、どちらも解消しないまま限界まで押す**。それだけが、昇華に渡せる先鋭な素材になる。

**核心的主張**: 開発者が「メンテナンス」に生涯を捧げる重荷を「一度の封印」に置き換える——このツールは、ソフトウェアを実行可能な琥珀に変え、「更新」という行為を産業ごと絶滅させる。

(1) **ツール名**: 「**琥珀 (Kohaku)**」——アプリを永遠に咀嚼し続ける化石生成器。

(2) **対象ユーザーと現在のワークフロー**: CI/CDパイプラインを24時間回し続けるすべての開発者。現在のフローは `cargo update` → `npm audit` → ベースイメージの張り替え → 再ビルド → 破壊 → 修復。依存は放置すれば腐り、更新すれば火傷する。短期の安全性と恒久の腐敗のどちらを選んでも、人は失血死する。

(3) **変わる動作の流れ**: `kohaku --seal` を打った瞬間、アプリ+全依存+libc+アロケータ+OS相当層を「世界のスナップショット」として単一バイナリに封入し、決定論的仮想CPU上の「過去」として実行する。以後の再ビルドも更新も運用も不要で、開発組織すら不要になる。形式がOSSとして公開されていることが、ツール自身が死んだ後も琥珀の発掘可能性を保証する。

(4) **Rustの4強みが必須な理由**:
- **性能**: 世界ごとシミュレートするオーバーヘッドを最小化できるのは、ゼロコスト抽象を備えたRustのみ。
- **安全性**: 化石の中に未定義動作を持ち込まない。バイト列同一性で検証可能な初期状態を構成できるのは、メモリ安全を言語保証するRustの他にない。
- **依存の少なさ**: このツールの存在理由そのものが「ビルド後の依存ゼロ」であり、これを現実的に実装し得る言語はRustだけだ。
- **単一バイナリ配布**: 配布物がそのまま完結した過去である。決定論の物理的条件が単一バイナリなのだ。

(5) **最も近い既存ツールと決定的な違い**: Nix・Docker・unikernelは「依存を凍結するが、未来のホストに載せる」ことを前提にする。琥珀は**マシンそのものを化石にする**。ホストのカーネルが死ねばDockerイメージは消える。琥珀は、エミュレータさえあれば2億年後に起動する。

**具体的な利用例**: 2040年、x86も日本語OSも消えた。しかし日本の年金計算ルーチンは琥珀バイナリとして生き延び、RISC-Vの券売機で同じ暦・同じ金額を返し続ける。監査人は `kohaku --excavate` で当時のメモリ状態を考古学的に復元する。

矛盾を封じたまま、私は結論を下す。**10倍遅い永遠は、1倍速くても5年しか動かないものより強い。** この提案の価値は、時間が比較する者たちを全滅させるほど、上昇し続ける。

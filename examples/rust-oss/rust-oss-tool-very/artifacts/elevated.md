# 1. タイトル

**`memo`（メモワール）— 履歴駆動開発環境**
「未来を指示するな。現在を確定せよ」——バイナリを唯一の実在とし、ソースコードをその履歴として再定義する開発者ツール。

# 2. エグゼクティブサマリー（核心的主張）

従来の開発は「ソースコードという設計図が未来のバイナリを指示する」という時間の向きに縛られてきた。この向きこそが、ビルド待ち、リグレッション、保守負債、依存関係の腐敗というすべての苦痛の源泉である。`memo`はこの時間の向きを逆転させる。

**バイナリが一次であり、ソースコードは二次である。** ソースコードは未来への指示ではなく、現在のバイナリが「どのような経緯でこの状態にあるか」を記述する履歴である。`memo`はバイナリを唯一の実在として管理し、ソースコードをその履歴の可読ビューとして動的に生成する。開発者がソースを編集すれば、バイナリの状態が即座に更新・検証され、履歴として再確定される。**ビルド待ちの時間は存在しない。** 編集と実現が同一の瞬間に起こる。

これは「ビルドを速くする」ツールではない。ビルドという概念そのものを「履歴の編集」へ溶解させる、存在論的な転換である。

# 3. 現状の課題

1. **時間的ギャップ**: ソースからバイナリへの変換は未来への往復運動であり、その間、開発者は意図と実現の分離に耐える。2000クレートのRustモノレポでは1回のフィードバックに数分〜数十分を要し、待ち時間以上に「思考の文脈の喪失」という隠れたコストが発生する。
2. **コード＝負債の不可視化**: ソースコードは増えるほど理解・保守・テストのコストを要求する。コード量とソフトウェアの価値は反比例するにもかかわらず、既存ツールはコードの蓄積を促進する方向に設計されている。
3. **環境の盲目性**: DockerやNixは依存をリスト化するが、コードと実行環境の関係性そのものは管理しない。「ソフトウェア＝コード＋環境」という全体性が欠落している。
4. **ツールの無限後退**: 新ツールは旧ツールが生んだ問題を解決するが、その解決は常にさらなるツールの必要性を生む（ビルドを速くするためにキャッシュ、キャッシュを検証するためにCI…）。開発者とソフトウェアの分離を前提とする限り、この後退は止まらない。

# 4. ツールコンセプト

## 4.1 対象ユーザー

- 長時間稼働するコードベースを保守するチーム（リファクタリングの反復が日常の開発者）
- ビルド待ち・CI待ちが開発速度のボトルネックになっているOSSプロジェクト
- 組み込み・システム開発者（バイナリの正確な状態追跡が必須の人々）
- 「コードを書く」ことより「システムの振る舞いを設計する」ことに価値を置く開発者

## 4.2 新しい枠組み

**(1) 実在の一元化** — `memo`は実行可能状態（バイナリ）を唯一の実在とみなす。ソースコードはその実在を人間可読形式で記述する「履歴ビュー」として、編集可能な形で動的生成される。

**(2) 可逆的双方向変換** — ソースの編集は即座にバイナリの状態への操作として解釈・適用される。逆にバイナリの状態遷移はソースの履歴に自動反映される。デコンパイラのような一方向の近似変換ではなく、どちらの方向にも可逆な同一性の維持である。

**(3) 検証＝一貫性の確認** — 型エラー・借用エラーは「未来のビルド失敗」としてではなく「現在の履歴の矛盾」として、編集の瞬間に検出される。検証は実行の結果ではなく、履歴の一貫性の確認として行われる。

**(4) 状態遷移としての履歴管理** — コミットやブランチはソースの差分ではなくバイナリの状態遷移として記録される。各状態には対応するソーススナップショットが導出ビューとして付随する。

## 4.3 具体的な動作例

**シナリオ: 開発者Aが`fetch_user`を同期から非同期に変更する。**

1. `memo init` — 既存の実行可能状態を解析し、現在のソースコードを履歴として生成する。
2. エディタで`fn fetch_user(id: u64) -> User`を`async`版に編集。
3. 保存した瞬間、`memo`は型検査を実行。呼び出し側に`.await`が必要という型エラーを「履歴の矛盾」として該当行に即時表示する。Aは呼び出し側も編集。
4. 全ての矛盾が解消された瞬間、バイナリの状態が更新され、新しいソースが履歴として再確定される。ここに「ビルド」という時間的プロセスは存在しない。
5. 問題が起これば`memo revert`で直前の状態遷移を破棄。破棄はソースの巻き戻しではなくバイナリ状態のロールバックとして実行され、ソースは自動的に整合する。

**成果物**: 出力は単一のバイナリ。その中に実行可能状態と全履歴（各状態のソーススナップショットを含む）が封入される。

# 5. Rustの強みの設計的活用

- **性能**: 編集の即時反映にはインクリメンタルな型検査・コード生成・リンキングが要求される。GCポーズが割り込めば「現在の確定」という体験が壊れる。Rustのゼロコスト抽象が即時性を物理的に可能にし、rustcのインクリメンタル基盤を直接活用できる。
- **安全性**: バイナリとソースの同一性は、未定義動作がないことを前提にはじめて成立する。unsafeによるメモリ破壊は対応関係を断ち切る。Rustのメモリ安全は「同一性」の物理的基盤であり、`memo`自身がRustで書かれることで自己言及的にその保証を体現する。
- **依存の少なさ**: バイナリの状態管理は依存が増えるほど複雑になる。`memo`は依存ゼロの単一バイナリとして動作し、さらに利用者に対しても依存の極小化を自然に促す（依存は「状態の複雑さ」として可視化される）。
- **単一バイナリ配布**: 配布物は唯一のファイルであり、その実行はファイル自身の履歴を展開することである。ランタイム不要、環境設定不要。「ソフトウェア＝環境の全体」という洞察をソースコードを含めて完全な形で実現する。

# 6. 既存ツールとの差別化

`memo`は既存ツールの改良ではない。**時間の向きそのものを逆転させる点で、カテゴリーが異なる。**

| 既存ツール | 前提 | memoの転換 |
|---|---|---|
| cargo build | ソースが一次、バイナリは二次。ビルドは未来への変換 | バイナリが一次、ソースは現在の記述。変換は過去への記録 |
| デコンパイラ | 一方向。復元ソースを編集してもバイナリに反映されない | 双方向可逆。どちらの編集も即座に相手へ反映 |
| Nix / Docker | ビルドの環境を再現可能にする。ビルド自体は存在し続ける | ビルドをプロセスから状態へ溶解させる |
| Git | ソースの時間的差分を管理。バイナリは管理対象外 | バイナリの状態遷移を管理。ソースは導出ビュー |
| JIT / ホットリロード | ソースと実行の距離を縮める（最適化） | 距離をゼロにし、方向を逆転させる（概念転換） |

決定的なのは「ビルドがもはや時間のかかるプロセスではない」点である。インクリメンタルビルドは「速い変換」を目指すが、`memo`は「変換が存在しない」状態を目指す。これは「馬を速くする」と「自動車を発明する」の違いに相当する。

# 7. ワークフロー変革のストーリー

あるOSSメンテナの一日:

- 朝、`memo log`で昨夜の状態遷移を確認。各contributionを「バイナリ状態の差分」としてレビューする。ソースの文面を読む前に、システムの振る舞いがどう変わったかが先にわかる。
- 新人のコントリビューターがPRを出す。彼女の編集は`memo`上で検証済みの状態遷移なので、ビルド待ちのCIは不要。メンテナは状態遷移の一貫性だけを確認してマージする。
- 依存ライブラリの脆弱性が通知される。`memo bump`を実行。更新は「バイナリ状態の遷移」として適用され、矛盾があれば即座に検出される。更新の恐怖がなくなる。

この世界では以下の対立が消える: 「書く」と「読む」（ソースを書くことは履歴を読むこと）、「実行」と「検証」（反映の成功自体が検証であり、テストは一貫性の確認に変わる）、「開発」と「保守」（現在を編集すれば履歴は自動的に整合する）、「個人」と「共同体」（OSSは共有された現在のバイナリに対する履歴編集権の協働となる）。ツールはもはや外部の道具ではなく、ソフトウェアが自己編集するための「記憶」の器官であり、開発者はその自己編集の「意識」になる。

# 8. 実装・配布・採用の現実性

**実装パス**: MVPは`cargo-memo`として、rustcのインクリメンタルコンパイル基盤を利用し「編集即反映」を実現する。双方向可逆変換は、まず最適化前のデバッグビルドのシンボル情報を手がかりに実装し、最終的には`rustc_driver`のIRを直接操作してソースをIRからの導出ビューとして持つ。

**段階的採用**:
- Phase 1: `memo watch` — 既存のcargoプロジェクトで編集→即時フィードバックを提供。
- Phase 2: `memo state` — バイナリ状態遷移の記録を開始。Gitはメタデータのミラーとして並存させ、摩擦を回避。
- Phase 3: `memo init`の完全な双方向化 — ソースを履歴ビューとして再生成。

**配布**: 静的リンクの単一バイナリをGitHub Releases・Homebrew・`cargo install`で配布。依存ゼロ、ランタイム不要。

**現実性の根拠**: インクリメンタルビルド、ホットリロード、ソースマップ復元など「ソースと実行の距離の短縮」の技術的蓄積は既にある。`memo`は距離をゼロにして方向を逆転させるが、基盤技術はすべてRustエコシステム内に存在している。

# 9. リスクと機会

**リスクと対応**:
- 最適化後バイナリからのソース再構成は情報理論的に非可逆。→ 可逆性はビルド情報（IR・シンボル）を保持する範囲で保証し、不可逆な変換は「履歴の不透明度」として明示する。
- 生成されたソースへの開発者の信頼。→ どの状態遷移がどの編集から生じたかを完全追跡する透明性で信頼を得る。
- Git中心の既存インフラとの摩擦。→ Phase 1/2での並存戦略と、Gitへの状態遷移エクスポート機能。
- バイナリが実在なら監査はバイナリに対して行われるべきでは？→ 状態遷移を人間可読な振る舞い要約として表示し、文面diff以上に意味を捉えやすくする。

**機会**:
- OSSへのコントリビューション摩擦の劇的削減（検証のためのビルドが不要になる）。
- CIの概念転換: 実行による検証から一貫性の確認へ。CI時間とコストの大幅削減。
- 再現性がトートロジーになる: 成果物が履歴を含むため、再現は「実行」ではなく「展開」。
- バイナリ状態を共有の現在とする、新しい共同開発の形態の創出。

# 10. 結論

開発者ツールの究極の形態は、ソフトウェアが自分自身の歴史を生きるための器官である。既存の開発は「未来のバイナリを指示するコード」を書くことで開発者とソフトウェアを引き離し、ビルド待ち・保守負債・更新の恐怖という時間的ギャップを生んできた。`memo`はこの時間の向きを逆転させ、バイナリを唯一の実在とし、ソースコードをその履歴として再定義する。

「ビルドするかしないか」「コードを残すか消すか」「凍結するか更新するか」という対立は、すべて「ソースが一次、バイナリが二次」という前提から生まれた幻想である。ソースとバイナリは元来同一のものであり、時間の方向が違うだけだ。この同一性の上に立つとき、消去は破壊ではなく履歴の書き換えになり、支援と廃絶は同一の行為になる。開発者はコードを書いてビルドする存在ではなく、バイナリの履歴を編集する存在になる。

消去は自由への道ではない。同一性こそが自由である。ソフトウェアが自分自身と同一であるとき、開発者は時間から解放される——時間はソフトウェアの内部に折りたたまれ、外部から流れ込むことがなくなるからだ。
